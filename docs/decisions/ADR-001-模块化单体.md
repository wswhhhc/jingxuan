# ADR-001：采用模块化单体而非微服务

## 状态

已接受

## 日期

2026-07-11

## 背景

现有系统功能完整但边界混乱，重复接口、跨模块直连 Mapper、根级 Service/Entity 与 `modules/*` 并存，维护成本高。目标是重构为可维护、可测试、可迁移的工程化结构，同时不引入额外基础设施负担。

## 决策

采用模块化单体，按业务拆分为：

- `identity-access`
- `reference-data`
- `campaign`
- `portfolio`
- `evaluation`
- `communication`
- `moderation`
- `operations-reporting`
- `workflow`

统一模块结构为 `api / web / internal.application / internal.domain / internal.infrastructure`。

约束：

- Controller 只能调用应用用例。
- 模块间只能依赖对方 `api`。
- 禁止跨模块注入 Mapper。
- 通过 Spring Modulith 和 ArchUnit 守卫依赖边界。

## 备选方案

### 微服务

- 优点：边界最强，独立部署。
- 缺点：引入配置中心、消息通信、服务治理、链路追踪等额外复杂度。
- 结论：超出当前团队与项目规模，不采用。

### 保持现状继续修补

- 优点：短期改动最小。
- 缺点：无法系统性解决边界失控和重复实现。
- 结论：只会继续放大后续迁移成本，不采用。

## 结果

- 保留单体部署简单性。
- 允许逐模块迁移和测试。
- 为阶段 2 之后的业务闭环重建提供稳定边界。
