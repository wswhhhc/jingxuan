# ADR-003：采用短期 Access JWT + 轮换 Refresh Token 的认证模型

## 状态

已接受

## 日期

2026-07-11

## 背景

现有系统使用 JWT，但刷新、登出、黑名单和角色边界都偏弱。重构后要保留三端角色能力，同时降低令牌泄露与接口重复的风险。

## 决策

- Access Token 为 JWT，有效期 15 分钟，只存前端内存。
- Refresh Token 为随机不透明令牌，Redis 仅保存哈希。
- 每次刷新轮换 Refresh Token，并检测重复使用。
- 默认会话 8 小时，“记住我”30 天。
- Refresh Cookie 限制：
  - `HttpOnly`
  - `SameSite=Strict`
  - `Path=/api/v1/auth`
  - 生产环境因 HTTP 风险接受 `Secure=false`
- 单账号单角色，角色带 `portalType`。
- 菜单只做导航，权限码和数据范围才是安全边界。

## 备选方案

### 仅使用长效 JWT

- 优点：实现简单。
- 缺点：撤销困难，泄露后风险窗口大。
- 结论：不采用。

### Session 存服务端

- 优点：撤销简单。
- 缺点：与当前前后端 SPA 架构和后续 API 契约链不匹配。
- 结论：不采用。

## 结果

- 认证与 RBAC 从“角色型路由”转为“权限码 + 数据范围”。
- 后续 `/api/v1` 可以统一资源路径，不必重复出三套接口。
